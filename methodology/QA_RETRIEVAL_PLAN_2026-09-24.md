## 2. Текущая архитектура (что есть)

Конвейер `query_directions` (`src/oa_snapshot.py:520-577`, CLI `scripts/oa_run_query.py`):

1. `topics` ← `taxonomy/topics.parquet` (4516 тем; blob = display_name + description + keywords);
2. `mega_mask` — хардкод-regex по ~12 именам generic-тем (`skip_mega=True`), маскирует скор в −1;
3. `match='embed'`: один вектор запроса `qv = LaBSE(query_ru)` → `sim = topic_vectors @ qv` (`taxonomy/topic_vectors.npy` 4516×768 + `topic_ids.txt`, нормализованные) → top-`n_topics`(60);
   `match='tfidf'`: sklearn TF-IDF (1,2)-грамм по blob + запрос → косинус (fallback, без модели);
4. top-60 тем → агрегация по `T_stats/year=*` (n_works, n_cites, y0/y1, фильтр years) → top-`topk`(50) направлений;
5. скоринг отдельно: `scripts/qa_protect_score.py` — substring-матч ключевых слов темы организатора в выдаче.

Ограничения окружения: RAM 7.4 ГБ, CPU 12, GPU нет; памятный лимит для DuckDB-прогонов `--threads 2 --mem 3GB`; внешние API с квотами — только по команде автора (внутренний контракт §8.1).

## 3. Диагноз: 3 точки отказа нестабильности

1. **Один вектор запроса на 16 гетерогенных подтем** (XAI ≈ приватность ≈ red-teaming ≈ EU AI Act ортогональны в embedding-пространстве). Один косинус не может быть близок ко всем; выигрывает ближайшее к «среднему» запроса — COVID/медицина (safety/protection), IoT, образование. Медианный ранг нужных тем ~251 при выдаче 50.
2. **`mega_mask` — неполный хардкод-regex**: COVID-мега-темы (несколько десятков тем × сотни тыс. работ) не в маске и доминируют.
3. **Скорер substring-based**: не засчитывает эквиваленты (Tier A/B), засчитывает ложные совпадения одним словом → оценка не отражает качество выдачи → тюнить вслепую.

Плюс: blob тем pred-Llama (нет LLM/RAG/red-team лексики) — лексические каналы в одиночку 12 не соберут; но Tier A+B эквиваленты в blob есть — их и надо ловить.

## 4. Целевая механика разбиения: fan-out подзапросов (И1, ядро плана)

Вместо `qv = encode(query)`:

```
направление «Защита ИИ» → словарь подзапросов directions.yaml (EN, из Tier A+B аудита):
  "privacy preserving technologies differential privacy"
  "adversarial robustness red teaming of ML models"
  "explainable AI interpretability safeguards"
  "EU AI Act governance compliance"
  "watermarking of machine-generated text"
  "homomorphic encryption trusted execution attestation"
  "access control identity management for software agents"
  "backdoor malware detection in machine learning models"
  "digital signature model provenance software supply chain"
  "cryptographic authentication protocol verification"
  "network intrusion detection firewall runtime gateway"
  ... (~12 подзапросов, по 1-2 на целевую тему)
каждый подзапрос: encode → top-K (K=5..10) тем → фьюжн рангов всех подзапросов
  (max-score по теме ИЛИ Reciprocal Rank Fusion) → top-60 → существующая агрегация статистик
```

**Почему это даёт стабильность:** каждый из 12 целевых получает **независимый канал** (свой вектор; ожидаемо в топ-K при общей лексике с blob — проверяется замером §7, НЕ гарантируется: blob pred-Llama). Провал одного канала не топит остальные — но пересечение каналов на слабых темах (EU AI Act, provenance) значит, что «разные каналы» ≠ полностью независимые. Точка отказа «1 вектор на 16 целей» убирается. **Источник словаря — первоисточник: 16 текстов `results/qa_target_protect_ai.json`** (формулировки организаторов), НЕ аудит; аудит даёт только allowed-sets для скорера (фикс аудита A.2/А-1: провенанс словаря ≠ разбор того же теста). Словарь — кэшируемый артефакт проекта, правится автором.

### 4а. Маршрутизация и телеметрия (фикс аудита A.4 / R-NEW-2)

- Фан-аут активируется только при сматченном направлении: детекция = точные RU/EN ключи словаря + семантический порог (LaBSE-cosine ≥ τ между запросом и каноническим названием направления; τ и ключи — фиксированный артефакт).
- **Результат маршрутизации (направление, score, fallback да/нет) — обязательное поле в JSON прогона** (телеметрия).
- Fallback при miss = одиночный вектор (= прогон 1) с явной пометкой «вне словаря».
- **Приёмка §7.2 считает прогон проваленным, если хотя бы одна из 3 формулировок ушла во fallback.**
- Мультиязычность: подзапросы словаря ведутся в RU и EN вариантах (embed — мультиязычный; BM25 — только по EN-варианту, см. §8.7).

## 7. Критерии приёмки (acceptance)

1. На прогоне «Защита ИИ»: **≥12/16 по allowed-sets** (Tier A+B), честно, без substring.
2. **Стабильность:** ≥12/16 на ≥3 вариантах формулировки запроса (рус. короткий / рус. длинный / англ.) — не только на канонической.
3. Детерминизм: повторный запуск того же запроса → та же выдача (кэш embed, фикс seed/версий); время ответа ≤ текущего порядка (CPU, без GPU).
4. ни одна COVID/медицина-мега-тема не в топ-20 (И5 подтверждается).
5. Отсутствующие #48/#52/#76 НЕ требуются к покрытию (зафиксировано в allowed-sets как out-of-scope с причиной); #4 (Tier C) — bonus только по явному решению автора.
6. **Ablation:** каждый из каналов И1/И3/И4 вносит ≥1 подтверждённую тему в union (иначе канал бесполезен — вырезается).

## 8. Риски и открытые вопросы (для аудита)

1. **Overfitting на один тест:** словарь подзапросов составлен из аудита того же теста — риск «заточки под единственный запрос». Митигация: регресс-сет из 3+ формулировок (п.7.2) + проверка на направлении не-теста (напр., «квантовые датчики») — план молчит о проверке на постороннем запросе? *(вопрос аудитору)*
2. **Gaming скорера:** allowed-sets — та же «ручная разметка», что и аудит; критик может указать, что порог становится самоисполняемым. Альтернатива: внешняя проверка (автор) на выдаче.
3. **Tier B — натяжки по определению** (5 из 12): если works-probe их не поднимет, фактический потолок без ручного засчёта = 7/16. Нужен план Б (какие каналы дают уверенность в T11689/T11504/T11693/T11241).
4. **Стоимость works-probe:** лексический скан abstracts 2024-2026 (year=2024..2026, T_text ~ десятки ГБ на E:) — влезает ли в 2 ГБ лимит/время; варианты: сузить до digest, кэшировать инвертированный индекс по годам.
5. **Пере-эмбеддинг blob'ов** (И2) меняет ранги ВСЕХ прошлых запросов — регрессия на старых смоук-запросах («сверхпроводимость…» эталон fusion #1/SC #2) обязательна; иначе сломаем смоук-базу.
6. **Кто генерирует/валидирует directions.yaml:** LLM (нужен ключ, п. И6) или автор вручную; чья семантика считается «истинной» для EN-формулировок.
7. **Не охвачено:** мультиязычность подзапросов (LaBSE мультиязычный, но BM25 — нет: RU-запрос × EN-blob не сматчится; нужен RU→EN перевод подзапросов заранее — в словаре они EN, а исходный запрос RU; кто переводит при авто-режиме?).
8. **Что делать после прохождения теста:** план оптимизирует QA-тест; связь с продуктовым выходом («ввод направления → список зарождающихся трендов», METHODOLOGY) — фан-аут должен стать общей механикой сервиса, а не костылем теста. *(обсудить с автором)*
9. **R-NEW-1: Невоспроизводимость эмбеддингов.** `_get_embedder` (`src/oa_snapshot.py:489`) — `local_files_only=False` без пиннинга ревизии: обновлённый/недоступный checkpoint LaBSE меняет все вектора → «детерминизм» §7.3 невозможен, регрессия необъяснима.
